# School ERP — Build Overview

Stack: **Node.js + Express (TypeScript) · React (Vite + TypeScript) · PostgreSQL on Neon · Prisma ORM · Capacitor for Android/iOS apps**

---

## 1. Big picture

```
                ┌──────────────────────────────────────────┐
                │        ONE React codebase (apps/web)       │
                │  role-based UI: Principal / Teacher / Parent│
                └───────┬───────────────┬───────────────┬───┘
                        │               │               │
                   Web browser     Android app      iOS app
                  (Vercel/Netlify)  (Capacitor)    (Capacitor)
                        │               │               │
                        └───────── HTTPS / JSON ────────┘
                                        │
                      ┌─────────────────▼──────────────────┐
                      │   Node + Express API (apps/api)     │
                      │  Auth (JWT) · RBAC · Zod validation  │
                      │  Modules: admission, fees, exams ... │
                      │  PDF engine · SMS/WhatsApp · Jobs    │
                      └───────┬───────────────┬────────────┘
                              │ Prisma        │
                     ┌────────▼──────┐  ┌─────▼───────────────┐
                     │ Neon Postgres │  │ File storage (R2/S3/ │
                     │               │  │ Cloudinary): photos, │
                     └───────────────┘  │ docs, generated PDFs │
                                        └──────────────────────┘
```

### Why Capacitor for the app ("same code")
Capacitor wraps the exact same React build into a native Android/iOS shell. One codebase → website + Teacher app + Student/Parent app. Native plugins give push notifications, camera (student photo / homework upload), file download and share. The UI is designed mobile-first so it feels right on phones.

> Alternative: Expo / React Native gives a more "native" feel but needs a separate UI codebase (only logic/types are shared). Not recommended for v1.

## 3. The three views (roles)

| | **Principal / Admin** | **Class Teacher** | **Student / Parent** |
|---|---|---|---|
| Scope | Whole school | Own class-section + subjects they teach | Own child(ren) only |
| Dashboard | Total strength, today's attendance %, fees collected today/month, pending dues, staff present, upcoming exams | Today's attendance status, timetable for today, pending homework checks, class birthday list | Child's attendance %, today's homework, fee due, next exam, notices |
| Main actions | Admissions, fee setup & collection, certificates, users & roles, salary, accounts, inventory, timetable, exam setup, reports | Mark attendance, post homework, enter marks, view/print students, notices to class, leave requests | View attendance/homework/timetable/results, download admit card & receipts, pay fees online, read notices, apply leave |
| Platform | Web (full), app (lite) | App first, web too | App first, web too |

**Extra staff roles** (from "Create users, roles / Multi user"): Principal can create users like *Accountant*, *Receptionist*, *Subject Teacher*, *Librarian* and tick permissions per role. Built as RBAC:

```
Role ──< RolePermission >── Permission (e.g. "fees.collect", "students.edit", "certificates.issue")
User ──< UserRole
```

Three **system roles** (Principal, Teacher, Parent) are fixed; custom roles are fully configurable. Every API route declares the permission it needs: `router.post('/fees/collect', can('fees.collect'), handler)`.

Parents: one login (mobile number + OTP or password) linked to all siblings, with a child switcher.

## 5. Data model (Prisma, core tables)

Every business table carries `schoolId` → the system is **multi-school (SaaS) ready** from day one, even if you start with one school. A middleware injects `schoolId` from the logged-in user so data never leaks between schools.

```
School ─┬─ AcademicSession (2025-26, isCurrent)
        ├─ Class (Nursery…XII) ── Section (A, B) ── classTeacherId → Staff
        ├─ Subject ── ClassSubject (class + subject + teacher)
        │
        ├─ User (login: phone/email, passwordHash) ─< UserRole >─ Role ─< RolePermission
        ├─ Staff (profile, designation, salary structure) ── userId
        ├─ Guardian (father/mother/guardian, phone) ── userId
        ├─ Student (admissionNo, name, DOB, photo, ...) ─< StudentGuardian >─ Guardian
        │     └─ Enrollment (student + session + section + rollNo)   ← promotion = new Enrollment
        │
        ├─ Enquiry, AdmissionDocument
        ├─ FeeHead, FeeStructure (class+session+head+amount+installment)
        │     StudentFeeDue (generated per installment) ─< Payment >─ Receipt
        │     Concession
        ├─ AttendanceDay (section + date) ─< AttendanceEntry (student, status)
        ├─ StaffAttendance
        ├─ Homework ─< HomeworkAttachment
        ├─ Exam ─< ExamSchedule (subject, date, maxMarks) ─< Mark (student, marks/grade)
        │     GradeScale
        ├─ Period, TimetableSlot (section, day, period, subject, teacher)
        ├─ CertificateTemplate, IssuedCertificate (type, serialNo, data snapshot)
        ├─ GatePass
        ├─ SalaryStructure, Payroll (month) ─< Payslip
        ├─ LedgerAccount, Transaction (income/expense, source = fee|salary|manual)
        ├─ InventoryItem, StockMovement
        ├─ Notice, Holiday
        ├─ SmsTemplate, SmsLog
        └─ AuditLog (who changed what)
```

Key design choices:
- **Enrollment per session** keeps history: a student's Class 6 records stay intact after promotion to Class 7.
- **Receipts and certificates store a data snapshot** so reprints match the original even if the student record changes later.
- **Money in paise (Int)**, never floats.
- Soft delete (`deletedAt`) for students/staff; audit log on fees, marks, certificates.

### Neon + Prisma setup
```prisma
datasource db {
  provider  = "postgresql"
  url       = env("DATABASE_URL")   // Neon *pooled* string (…-pooler…) for the running app
  directUrl = env("DIRECT_URL")     // Neon *direct* string for `prisma migrate`
}
```
Both strings go in `apps/api/.env` (git-ignored). Neon branching can give a separate `dev` database branch.

## 6. Backend details

| Concern | Choice |
|---|---|
| Framework | Express + TypeScript, modular folders (`routes.ts`, `service.ts`, `schema.ts` per module) |
| Validation | Zod (shared with frontend) |
| Auth | JWT access token (15 min) + refresh token (httpOnly cookie on web, secure storage on app); bcrypt passwords; OTP login for parents (phase 2) |
| Authorization | `auth` → `tenant` → `can('permission')` middlewares; teachers additionally restricted to their own sections |
| PDFs | HTML + CSS templates rendered by Puppeteer → handles Hindi (Devanagari) text correctly; used for receipts, marksheets, TC/CC/DOB, I-cards, admit cards, payslips |
| Background jobs | `pg-boss` (runs on Postgres, no Redis needed): bulk SMS, bulk I-card/marksheet generation |
| SMS | Provider adapter (MSG91 / Fast2SMS — DLT-registered templates for India); WhatsApp adapter later |
| Files | S3-compatible storage (Cloudflare R2 / AWS S3) or Cloudinary for photos |
| Exports | Excel via `exceljs`; Excel import for bulk students |
| API docs | OpenAPI generated from Zod schemas |

## 7. Frontend details

| Concern | Choice |
|---|---|
| Build | Vite + React + TypeScript |
| UI | Tailwind CSS + shadcn/ui, mobile-first, bottom tab bar on phones, sidebar on desktop |
| Data | TanStack Query (caching, offline-friendly), Axios client |
| Forms | React Hook Form + Zod resolver |
| Routing | React Router with role guards (`/principal/*`, `/teacher/*`, `/parent/*`) |
| Language | i18n with **English + Hindi** toggle |
| Charts | Recharts for dashboards |
| Mobile | Capacitor: Push Notifications (FCM), Camera, Filesystem/Share (download receipts & admit cards) |

## 8. Build phases

| Phase | Deliverable |
|---|---|
| **1. Foundation** | Monorepo, Prisma schema + Neon migrations, auth, RBAC, school settings, sessions, classes/sections/subjects, 3 role layouts, seed data |
| **2. Students & Admission** | Enquiry, admission form, student list/profile, guardians & parent login, Excel import, promotion |
| **3. Fees** | Fee heads/structure, dues generation, collection, receipt PDF, due list, concessions, fee reports |
| **4. Daily academics** | Attendance (+ SMS), homework, timetable, notices, parent app screens |
| **5. Exams** | Exam plan, date sheet, admit card, marks entry, grading, marksheet PDF, results to parents |
| **6. Documents** | TC, CC, DOB, bonafide certificates, I-card, gate pass, template editor |
| **7. Staff & Money** | Staff, staff attendance, salary/payslips, accounts ledger, inventory |
| **8. Reports & Apps** | Report builder, dashboards, Capacitor Android/iOS builds, push notifications, online fee payment |

Each phase is usable on its own — after Phase 3 a school could already run admissions and fee collection.

## 9. Deployment

- **API**: Render / Railway / a small VPS (Puppeteer needs a normal Node server, not edge functions)
- **Web**: Vercel / Netlify (static Vite build)
- **DB**: Neon (pooled connection for app)
- **Apps**: `npx cap sync` → Android Studio → Play Store; Xcode → App Store
- **Env**: `DATABASE_URL`, `DIRECT_URL`, `JWT_SECRET`, `SMS_API_KEY`, `STORAGE_*`, `FCM_*`
